# 設計：GitHub Actions による CI

- 日付: 2026-08-24
- 対象: `.github/workflows/ci.yml`（新規）

---

## 目的

`pytest` と `npm run lint` / `npm run build` を、手元で思い出したときではなく **PR ごとに自動で** 走らせる。

狙いは「壊れたコードが main に入らない」こと、そして毎回まっさらな Linux から始めることで
**clone してきた状態で本当にビルド・テストできるか** を証明することにある。手元の `.venv` や
起動しっぱなしのローカル PostgreSQL に依存して通っているだけ、という状態を検出できる。

---

## 方式の選択

ワークフローの分割方法として3案を比較し、**A** を採る。

| 案 | 内容 | 採否 |
|---|---|---|
| **A** | 単一 `ci.yml` に backend / frontend の2ジョブを並列。パスフィルタなし | **採用** |
| B | `backend.yml` / `frontend.yml` に分け、`paths:` で変更時のみ実行 | 不採用 |
| C | 1ジョブで backend も frontend も直列実行 | 不採用 |

A を採る理由：

- 1ファイルで全体が読め、2ジョブは並列に走るので実時間は遅いほうのジョブで決まる
- B の `paths:` はワークフロー単位の設定なのでファイル分割が前提になる。さらに、branch protection の
  必須チェックに指定したジョブが paths でスキップされると、チェックが pending のままマージできなくなる。
  回避するには「常に成功するダミージョブ」などの小細工が要り、今の規模では割に合わない
- C は Python と Node の両方をセットアップする分だけ遅く、backend が落ちると frontend が未検証のまま終わる

ジョブが増えて実行時間が問題になったら B へ移せばよい。その判断は今ではない。

## トリガと同時実行制御

```yaml
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read
```

- `pull_request` は **PR ブランチと main をマージした結果** の状態を検証する。レビュー対象そのものが対象になる
- `push: [main]` はマージ後にもう一度回す。main が壊れた瞬間に気づける
- `concurrency` は同一ブランチへの連続 push で古い run を打ち切る。無駄な実行時間を積み上げない
- `permissions` は読み取りのみ。デプロイもコメント投稿もしないので最小権限で足りる

## backend ジョブ

`backend/tests/conftest.py` は **本物の PostgreSQL** を要求する。接続先は `TEST_DATABASE_URL`
（既定 `postgresql://misnote:misnote@localhost:5432/misnote_test`）で、`misnote_test` が無ければ
自分で `CREATE DATABASE` し、`Base.metadata.create_all()` でテーブルを作る（Alembic は通さない）。

したがって CI が用意するのは **空の PostgreSQL サーバ1台だけ** でよい。

- service container で `postgres:16` を起動する（`docker-compose.yml` の `db:` と同じ役割）
- ステップは runner のホスト側で走るため `ports: - 5432:5432` の公開が必須
- `--health-cmd pg_isready` を指定し、healthy になるまでステップを開始させない。書かないと接続拒否で落ちる
- `POSTGRES_USER` / `POSTGRES_PASSWORD` は `docker-compose.yml` と揃え、ローカルと CI で挙動を変えない
- `python-version` は `backend/Dockerfile` の `python:3.12-slim` に合わせる。本番と違う Python で
  テストしても意味が薄い。手元の venv は 3.14 なので、**CI は手元と別バージョンで回る**点は意識しておく
- `requirements-dev.txt` は1行目が `-r requirements.txt` なので、これ1つで本体も dev も入る
- `app/config.py` の `database_url` / `secret_key` は両方ともデフォルト値を持つため、Secrets は不要

## frontend ジョブ

Node だけあればよい。DB もバックエンドの起動も要らない。

- 型付きクライアント `src/generated/` がコミット済みのため、OpenAPI からの再生成が不要。
  したがって Java も openapi-generator も CI には要らない
- `src/lib/api.ts` の接続先は `process.env.NEXT_PUBLIC_API_BASE_URL ?? "http://localhost:8000"` と
  デフォルト付きなので、ビルド時に環境変数を渡さなくても落ちない
- 依存のインストールは **`npm ci`**。`package-lock.json` の通りに入れ、lock を書き換えず、ズレていれば
  エラーで止まる。`npm install` だと `^16.2.9` が新しい 16.x を拾い「手元では通るのに CI だけ落ちる」が起きる
- lint を build より前に置く。lint は数十秒、build は数分で、速いほうが先だと単純なエラーで待たされない。
  ステップは直列なので、1回の run で分かる失敗は1つ、という割り切りを受け入れる
- **型チェックは `next build` が兼ねる**。`tsc --noEmit` は足さない
- `node-version: "22"`（現行 LTS）。Next.js 16 は Node 20.9 以上を要求する

## ブランチ保護

ワークフローを置くだけでは赤でもマージできる。Settings → Branches → main のルールで
**Require status checks to pass before merging** を有効化し、次の2つを必須チェックに指定する。

- `backend (pytest)`
- `frontend (lint + build)`

一覧に出る名前はジョブの `name:` の値。**一度も実行されていないチェックは一覧に出ない**ため、
「PR を1本通して初回実行 → その後で保護ルールを設定」の順になる。

---

## 今回やらないこと

意図的な不採用。まず「壊れたコードが main に入らない」土台を1つ確立してから足す。

- `backend/openapi.json` とコードのドリフト検知
- Docker イメージのビルド確認
- ruff などの backend lint（依存追加ゼロを優先。既存コードの整形差分も発生させない）
- カバレッジ計測、複数バージョンのマトリクステスト
- Dependabot
- デプロイ（Phase 4 の CD）

## 検証

CI は動かすまで正しいと言えない。手元で通してから載せる。

1. `cd backend && pytest -q` が緑 → **131 passed** で確認済み
2. `cd frontend && npm run lint && npm run build` が緑 → いずれも終了コード 0 で確認済み
   （lint は `src/generated/` の unused eslint-disable 警告が3件出るが error 0 のため CI は落ちない）
3. `ci.yml` を足したブランチで PR を開き、2ジョブとも緑になることを確認する
4. 緑を確認してからブランチ保護を設定する
5. わざと lint エラーを入れた PR を1本作り、**赤くなることとマージがブロックされること**を確認して戻す

5 を省くと「CI が落ちるべきときに落ちる」ことが未確認のままになる。CI があることの証明にはならない。
